# 即時推播（Pub/Sub）可行性評估

> 任務：[1-可行性分析.md](1-可行性分析.md)：儀器資料由後端程式寫入 DB，評估能否用訂閱/發佈更新前端（排除 HTTP Long Polling）。
> 日期：2026-11-06

## 結論：可行
現有架構不必改動任何元件就能做，只要多一條推播路徑：

```
採集程式 ──INSERT──▶ PostgreSQL ──(trigger → NOTIFY)──▶ backend (sqlx PgListener)
                                                         │ tokio::sync::broadcast（行程內 fan-out）
                                                         ▼
Browser ◀──SSE (text/event-stream)── Cloudflare Tunnel ◀── axum GET /api/stream
```

| 環節 | 採用 | 可行依據 |
|---|---|---|
| DB → backend | PostgreSQL `LISTEN/NOTIFY` + `AFTER INSERT` trigger | PostgreSQL 內建；sqlx 0.8 的 `postgres` feature 已含 `PgListener`，不需新依賴 |
| backend 內 fan-out | `tokio::sync::broadcast` | tokio 內建，一個 listener 對 N 個連線 |
| backend → browser | **SSE** | axum 0.8 內建 `axum::response::sse`（含 `KeepAlive`），不需開 feature |
| 穿越 Tunnel | Cloudflare Tunnel 支援 streaming response 與 WebSocket | 不需開 inbound port，維持現有安全模型 |
| 前端訂閱 | 瀏覽器原生 `EventSource`（`web-sys`） | 斷線自動重連、`Last-Event-ID` 由瀏覽器自動帶上 |

## 為何選 SSE 而非 WebSocket
- 資料流是**單向**（server → client），前端不需要上行訊息，WebSocket 的雙向能力用不到（YAGNI）。
- SSE 是普通 HTTP response，CORS、Cloudflare 快取規則、tracing 都沿用既有 middleware。
- 瀏覽器內建重連與 `Last-Event-ID`，WebSocket 這些都要自己寫。
- 瀏覽器到 Cloudflare edge 走 HTTP/2/3，沒有 HTTP/1.1「每網域 6 條連線」的限制。
- 何時改用 WebSocket：前端需要上行指令（例：遠端調整儀器參數）時。axum 開 `ws` feature 即可，DB/broadcast 這兩層不用改。

## 關鍵設計點
1. **觸發點放在 DB trigger，不放在採集程式**：採集程式只管 INSERT，不必知道推播的存在。之後換語言或換程式都不影響推播；手動補資料也會推播。
2. **NOTIFY payload 只帶 `reading_id`（或精簡 DTO）**：payload 上限 8000 bytes。backend 收到 id 後查 DB 組 DTO，DTO 放 `shared` crate，前後端共用。
3. **不漏資料**：SSE event 的 `id:` 填 `reading_id`。重連時瀏覽器會帶 `Last-Event-ID`，backend 先從 DB 補送 `id > last` 的資料，再接即時流。`NOTIFY` 本身不保證送達，這一步補了這個缺口。
4. **心跳**：Cloudflare 對閒置連線約 100 秒會斷線。資料每小時才一筆，一定會碰到，所以用 `Sse::keep_alive` 每 15–30 秒送一次註解行。
5. **慢消費者**：`broadcast` 的 receiver 落後會收到 `RecvError::Lagged`。處理方式是改走「從 DB 補送」的流程，不讓連線斷掉。
6. **PgListener 斷線**：sqlx 會自動重連，但重連期間的 NOTIFY 會遺失。重連後對所有訂閱者送一個 `resync` event，前端收到後依 `Last-Event-ID` 重新補資料。

## 風險與對策
| 風險 | 影響 | 對策 |
|---|---|---|
| Cloudflare 緩衝 streaming response | 事件延遲到達 | 回應帶 `Content-Type: text/event-stream`、`Cache-Control: no-cache`；PoC 實測端到端延遲 |
| Cloudflare 100 秒閒置逾時 | 連線頻繁斷開 | keep-alive 心跳（見設計點 4） |
| 前端（Pages）與 API 不同 origin | `EventSource` 被 CORS 擋 | 既有 `tower-http` CORS 加白名單 Pages 網域 |
| 若日後需要登入 | `EventSource` 不能帶自訂 header | 改用 HttpOnly cookie，或用短期 token 放 query string。對應 Open Question #4 |
| 同時連線數 | 每條連線各占一個 tokio task | 每小時一筆資料，負載可忽略；PoC 會量測 1000 條連線下的記憶體 |

## 與滾動式計畫的關係
- 部分回答了 Open Question #2：採集程式**直寫 DB**，推播由 DB trigger 觸發。兩者不衝突。
- 前提依賴 Phase 2 的 `readings` schema。建議把推播排在 Phase 3（查詢 API）之後、與 Phase 4（前端圖表）一起做，因為補送邏輯與歷史查詢 API 共用同一個查詢。

## 驗證計畫（PoC）
在 schema 確定之前，用一張暫時的表 `poc_readings(id bigserial, value double precision, recorded_at timestamptz)` 驗證整條鏈路。PoC 程式碼放 feature branch，不 merge 進 `main`。

| # | 步驟 | 驗收條件 |
|---|---|---|
| P1 | migration：建暫時表 + `AFTER INSERT` trigger `pg_notify('readings', NEW.id::text)` | `psql` INSERT 後，另一個 session `LISTEN readings` 收得到 |
| P2 | backend：啟動時 spawn `PgListener` task → `broadcast::Sender` 放進 `AppState` | 單元測試：送進 sender 的訊息，subscriber 收得到 |
| P3 | `GET /api/stream`：SSE + keep-alive + `Last-Event-ID` 補送 | 整合測試（測試 DB）：INSERT 後 1 秒內收到 event；用 `Last-Event-ID` 重連時補齊缺漏 |
| P4 | 本機 cloudflared tunnel 對外，`curl -N https://api.<domain>/api/stream` | 端到端延遲 < 2 秒；閒置 10 分鐘不斷線 |
| P5 | 前端 `web-sys::EventSource` 小元件顯示最新值 | 線上 Pages 頁面即時更新；關掉 backend 再開啟後能自動重連並補資料 |
| P6 | 壓力：1000 條並行 SSE 連線 | backend RSS 增量與 CPU 記錄於本檔 |

前置條件：P4 需要已掛在 Cloudflare 的網域（Open Question #6）；沒有網域時可先用 `cloudflared tunnel --url`（quick tunnel）驗證。
