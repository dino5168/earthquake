# 地震點雲整合進網站「歷史查詢」— 實作計畫

> 任務單：`1-Plans/5-將地震點雲放到正是網站.md`
> 前置：`1-Plans/4-地震點雲3D實作計畫.md`（eq-3d 原型已完成）
> 目標頁面：https://earthquake-cm9.pages.dev/history（目前是 `MenuRoutePage` 佔位頁）

## 1. 現況
| 項目 | 現況 |
|---|---|
| 網站前端 | Leptos 0.8 CSR（WASM），由 Trunk 建置，`/history` 走 fallback 佔位頁 |
| 3D 原型 | `4-資料處理/eq-3d/`：Vite + TS + three.js，獨立 HTML 頁面，HUD 用 `position: fixed` |
| 資料 | `EQHistory.csv` 3.8 MB（gzip 後 1.0 MB）、`terrain.bin` 0.84 MB（gzip 後 0.56 MB），兩者都被 gitignore |
| 佈署 | GitHub Actions：`trunk build` → wrangler 上傳 `dist/` 到 Cloudflare Pages；CI 只裝 Rust，沒有 Node |

## 2. 整合方式比較與建議
| 方案 | 做法 | 優點 | 缺點 |
|---|---|---|---|
| **A. iframe（建議）** | eq-3d 照原樣建置成靜態子站 `/viz/eq-3d/`，`/history` 頁用 `<iframe>` 嵌入 | 原型幾乎不用改；three.js 不進主 WASM bundle，只有開啟 `/history` 才載入；離開頁面時 iframe 卸載，WebGL 資源自動釋放；CSS 完全隔離 | 多一層 iframe；之後要和 Leptos 頁面互動（例如篩選條件同步）得用 `postMessage` |
| B. JS 模組掛載 | eq-3d 改成函式庫，匯出 `mount(el)` 和 `dispose()`，Leptos 透過 `wasm-bindgen` 呼叫 | 沒有 iframe，可以直接互動 | 要改寫生命週期，換頁時必須手動 dispose，否則 WebGL context 外洩；lil-gui 和 HUD 要從 `fixed` 改成相對容器定位；Trunk 要處理 JS 模組雜湊檔名 |
| C. Rust 重寫 | 用 `three-d` 或 `web-sys` WebGL 重做 | 單一技術棧 | 工作量最大，重做已經驗收的視覺效果，不划算 |

**建議方案 A。** 目前沒有「3D 和頁面其他元件互動」的需求（YAGNI）。日後真的需要時，再用 `postMessage` 擴充，不需要換方案。

## 3. 目標架構
```
9-Project/
  viz/eq-3d/                 ← 從 4-資料處理/eq-3d 搬過來（網站程式碼歸 9-Project；資料前處理腳本留在 4-資料處理）
    vite.config.ts           base: "/viz/eq-3d/"
    public/data/             EQHistory.csv、terrain.bin/json → 進版控（CI 拿不到 50 MB 原始 XML）
    scripts/update-data.mjs  從 4-資料處理 的產出更新 public/data（資料更新時手動執行，再 commit）
  crates/frontend/
    src/pages/history.rs     HistoryPage：iframe 填滿內容區
    styles/pages/_history-page.scss
    src/app.rs               新增 /history 路由
    index.html               Trunk copy-dir：../../viz/eq-3d/dist → dist/viz/eq-3d

CI（deploy-frontend.yml）：
  checkout → setup Node 22 + pnpm → pnpm build (viz/eq-3d) → trunk build → 上傳 dist
  觸發路徑新增 9-Project/viz/**
```
- Pages 會優先提供實體檔案，所以 `/viz/eq-3d/index.html` 直接回應，不會被 SPA fallback 攔截。
- iframe 內偵測 `window.self !== window.top` 時，隱藏自己的標題，因為 Topbar 已經顯示「歷史查詢」。圖例、控制面板、資料出處照常顯示。

## 5. 可行性評估
**可行**，沒有阻擋性風險。

| 項目 | 評估 |
|---|---|
| 頁面大小 | three.js 約 147 KB（gzip）＋資料約 1.56 MB（gzip），只有開啟 `/history` 時才載入；Cloudflare 會自動壓縮。首頁的 WASM 完全不受影響 |
| Pages 限制 | 單檔上限 25 MB、檔案數上限 20,000，都遠低於上限 |
| 版控 | 資料進 git 約 4.7 MB，之後每年更新一次，成長很慢，可以接受 |
| CI 時間 | 多了 Node 安裝和 pnpm 快取，預估多 30–60 秒 |

| 風險 | 對策 |
|---|---|
| 手機 GPU 效能和小螢幕操作 | T6 用手機寬度實測；必要時在窄螢幕預設收合 lil-gui |
| 本機要先 build viz，`trunk serve` 才找得到 copy-dir 來源 | 在 Trunk `pre_build` hook 檢查；找不到 dist 時印出提示 |
| 資料更新後忘了 commit | `update-data` 腳本最後印出提醒，並把資料更新流程寫進 `9-Project/docs` |
| 日後 Phase 3 歷史查詢 API 上線 | 屆時資料來源從靜態 CSV 改成 API，iframe 方案和 viewer 架構都不用變 |
