# 滾動式計畫 Rolling Plan

> 原則：**當前階段**細到任務級；**下一階段**到目標級；**後續階段**一行。
> 每完成一個階段就「滾動」：當前階段歸檔 → 下一階段展開為任務 → 補上新的後續階段。
> 上限 200 行；已完成階段細項移至 `archive/plan-phase-N.md`。

參考：[[1-地震監測網]]

## Phase 2 — 資料模型與寫入（當前，待 Open Questions）
目標：確定感測器資料格式，完成 DB schema 與資料寫入路徑。
- 釐清 Open Questions（見下）
- 設計 `sensors` / `readings` schema 與 index，撰寫 migration
- 實作寫入路徑（依決策：API ingest 或感測器直寫 DB）
- 本地 PostgreSQL 開發環境（docker compose 或內網 DB）

## 後續階段（一行）
- Phase 3 — 歷史查詢 API（時間區間、感測器篩選、分頁/降採樣）
- Phase 4 — 前端查詢頁與圖表（套用 Phase 1 外框）＋即時推播 SSE（評估見 `3-可行性分析/2-即時推播評估計畫.md`）
- Phase 5 — 部署：Cloudflare Tunnel + 內網服務化（Windows Service / systemd）、前端綁自訂網域
- Phase 6 — 「未來可能發生情形」分析/預警（需求待定義）

## Open Questions（需使用者決定）
1. 感測器資料欄位？（例：加速度三軸、地磁、地下水位、氡氣濃度…）感測器數量與位置？
2. 寫入方式：感測器/採集程式**直寫 DB**，或經**後端 ingest API**（建議 API，便於驗證與權限控管）？
3. 內網主機 OS（Windows / Linux）？PostgreSQL 是否已存在？是否可裝 PostGIS（位置資料）？
4. 前端是否需要登入？或公開查詢？
5. 「監測未來可能發生的情形」的具體定義：閾值告警、趨勢圖、或預測模型？
6. 網域：是否已有掛在 Cloudflare 的網域（API 子網域如 `api.<domain>`）？
